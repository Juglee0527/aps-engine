# APS Schedule Control Tower

## 1. 목적

현재 구현된 APS API를 개발 도구 없이 브라우저에서 운영하고 검증하기 위한 Control Tower 화면입니다.
화면의 오더, 작업, 납기 지연, CAPA 사용률은 예시 숫자가 아니라 실제 API 응답으로 계산합니다.

## 2. 기술 선택

MVP 화면은 Spring Boot의 정적 리소스 기능을 사용하며 HTML, CSS, Vanilla JavaScript로 구성합니다.

- 서버 실행 한 번으로 API와 화면을 함께 확인할 수 있습니다.
- Node.js, npm 및 별도 프론트엔드 빌드 파이프라인이 필요하지 않습니다.
- 현재 화면 규모에서는 프레임워크 상태 관리보다 명시적인 계층 선택 흐름이 단순합니다.
- 향후 화면과 상호작용이 충분히 커지면 React 등 별도 프론트엔드 전환을 검토합니다.

프론트엔드 프레임워크 전환은 현재 요구사항이 아니므로 MVP에 포함하지 않습니다.

## 3. 화면 범위

```text
Master Data
  → Factory · ProductionLine · Machine
  → Product · Routing · Operation
  → WorkingCalendar
  → ProductionOrder 등록·확정
    → Forward Scheduling 실행
      → 설비별 Gantt · CAPA · 납기 지연
```

- 스케줄 보드는 확정 대기 오더, 배정 작업, 납기 지연, 최우선 병목 후보를 보여줍니다.
- 실행 모달에서 명시적 우선순위, 납기 우선(EDD), 최단 가공시간 우선(SPT) 중 하나를
  직접 선택하며 서버가 규칙을 자동 추천하지 않습니다.
- 실행 결과 배너에서 적용 규칙, 총 납기 지연시간, Makespan과 계획 설비 가동률을 함께 비교합니다.
- 설비별 간트는 저장된 최신 스케줄의 가공 시작·종료, Changeover 준비작업, 오더 구분과 지연 여부를 표현합니다.
- 설비 부하는 계획기간의 `(가공 분 + Changeover 분) / 가용 분`으로 표시하고, 병목 순위와
  사유는 백엔드 Bottleneck Detection API 결과를 사용합니다.
- 간트와 CAPA 조회는 실행에 저장된 계획 UTC offset을 사용하므로 브라우저 위치와 무관하게 공장 현지시각을 유지합니다.
- 생산오더 화면에서 DRAFT 오더를 확정할 수 있습니다.
- 마스터 화면에서 공장, 라인, 설비, 품목, Routing과 주간 근무시간을 등록할 수 있습니다.
- 사용자 가이드에서 샘플 데이터를 4단계로 등록하고 각 단계의 진행 상태를 확인할 수 있습니다.
- API 오류는 화면 알림으로 표시하고 서버 연결 상태를 왼쪽 하단에서 확인할 수 있습니다.

## 4. 샘플 온보딩

처음 사용하는 사용자는 각 등록 화면을 오가며 값을 직접 입력하지 않고 사용자 가이드의
샘플 온보딩을 따라 첫 스케줄을 만들 수 있습니다.

```text
1. DEMO-FACTORY · DEMO-LINE · 절단/조립 설비 · 월~금 근무시간
2. DEMO-PRODUCT · DEMO-ROUTING · 절단 → 조립 공정
3. 우선순위가 다른 확정 생산오더 2건
4. Forward Scheduling 실행 · 스케줄 보드 확인
```

- 한 단계가 완료되어야 다음 단계 버튼이 활성화됩니다.
- 등록 중인 항목과 완료 단계는 진행 로그와 진행률로 표시합니다.
- 샘플 코드를 가진 데이터가 이미 있으면 새로 만들지 않고 재사용합니다.
- 단계 도중 요청이 실패해도 완료된 데이터는 유지하며 같은 단계에서 이어서 진행합니다.
- 기존 데이터는 수정하거나 삭제하지 않습니다.
- 직접 입력하려는 사용자는 기존 마스터 데이터와 생산오더 등록 화면을 그대로 사용할 수 있습니다.

샘플 값과 단계 제어는 브라우저 코드에만 있으며, 별도의 샘플 전용 백엔드 API를 추가하지 않습니다.
각 등록은 기존 `/api/v1/**` 계약을 그대로 사용하므로 실제 운영 흐름과 같은 검증을 거칩니다.

## 5. 데이터 흐름

화면은 동일 출처의 `/api/v1/**` API를 호출합니다. 별도 프록시나 CORS 설정은 필요하지 않습니다.
등록 성공 후 해당 계층을 다시 조회해 서버 데이터를 화면 상태의 기준으로 사용합니다.

최초 로딩 시 각 목록을 최대 100건 조회합니다. 이는 운영용 전체 목록 정책이 아니라 현재 MVP의
간단한 탐색 범위입니다. 실제 데이터가 100건을 넘는 단계에서는 검색과 페이지 이동 UI를 별도로 설계합니다.

## 6. 제외 범위

- 사용자 인증과 권한
- 기준정보 수정 및 삭제
- 스케줄 확정, 취소와 재스케줄링 이력 비교
- Drag & Drop 수동 재배치
- Maintenance와 대체 설비 시각화
- 서버 푸시 또는 실시간 자동 갱신

## 7. 실행 및 확인

PostgreSQL을 실행하고 로컬 프로필로 애플리케이션을 시작한 다음
`http://localhost:8080`에 접속합니다.

```powershell
docker compose up -d postgres
.\scripts\run-local.ps1
```

처음 실행한다면 `사용자 가이드`에서 샘플 온보딩의 1~4단계 버튼을 순서대로 누릅니다.
직접 검증하려면 마스터 데이터를 구성하고 생산오더를 확정한 뒤 스케줄을 실행합니다.
최신 실행 ID, 설비별 간트, 오더 상태와 CAPA 부하가 API 데이터와 일치하는지 확인합니다.
