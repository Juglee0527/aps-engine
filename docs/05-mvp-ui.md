# APS Schedule Control Tower

## 1. 목적

현재 구현된 APS API를 개발 도구 없이 브라우저에서 운영하고 검증하기 위한 Control Tower 화면입니다.
화면의 오더, 작업, 납기 지연, CAPA 사용률은 예시 숫자가 아니라 실제 API 응답으로 계산합니다.

## 2. 기술 선택

MVP 화면은 Spring Boot의 정적 리소스 기능을 사용하며 HTML, CSS, Vanilla JavaScript로 구성합니다.

- 서버 실행 한 번으로 API와 화면을 함께 확인할 수 있습니다.
- Node.js, npm 및 별도 프론트엔드 빌드 파이프라인이 필요하지 않습니다.
- 브라우저 코드는 네이티브 ES Module로 로딩하며 API, 상태, 공통 UI, 스케줄 보드,
  생산오더, 기준정보와 사용자 가이드 책임을 파일 단위로 분리합니다.
- 현재 화면 규모에서는 프레임워크 상태 관리보다 명시적인 계층 선택 흐름이 단순합니다.
- 향후 화면과 상호작용이 충분히 커지면 React 등 별도 프론트엔드 전환을 검토합니다.

프론트엔드 프레임워크 전환은 현재 요구사항이 아니므로 MVP에 포함하지 않습니다.

### UI 디자인 기반

UI 현대화 `060`부터 색상, 간격, 모서리, 그림자, 포커스와 상태 색을 CSS custom property로
관리합니다. 버튼, 입력, 상태 배지, 카드, 패널, 표와 dialog는 같은 토큰을 사용하며 문자 기호 대신
외부 의존성이 없는 inline SVG 아이콘을 사용합니다. 한글 데이터의 가독성을 위해 공통 컨트롤과 표의
기본 글자 크기를 높이고 키보드 포커스를 모든 공통 컨트롤에서 확인할 수 있게 했습니다.

`061`부터 앱 셸은 248px 데스크톱 사이드바와 최대 1640px 작업 영역을 사용합니다. 980px 이하에서는
상단 브랜드 바와 접을 수 있는 메뉴로 바뀌고, 680px 이하에서는 메뉴를 2열로 재배치합니다.
고정 1180px 최소 폭은 제거했습니다. Context Header는 현재 화면의 목적을 설명하며 스케줄 실행처럼
해당 화면에서만 의미 있는 행동은 다른 화면으로 이동하면 숨깁니다.

`062` 스케줄 Control Tower는 최신 실행을 상태·설명 영역과 8개 실행 메타로 분리합니다. 실행 결과가
없을 때는 기준정보, 확정 생산오더와 샘플 실습으로 연결되는 첫 계획 체크리스트를 표시합니다. 결과가
생기면 체크리스트는 사라지고 계획 규칙, 총 지연, Makespan과 가동률을 먼저 읽을 수 있습니다.
납기 지연이 있으면 KPI 카드가 경고 상태로 바뀌어 병목과 함께 우선 검토할 대상을 드러냅니다.

## 3. 화면 범위

```text
Master Data
  → Factory · ProductionLine · Machine
  → Product · Routing · Operation
  → WorkingCalendar
  → ProductionOrder 등록·확정
    → Forward Scheduling 실행
      → 설비별 Gantt · CAPA · 납기 지연
```

- 스케줄 보드는 확정 대기 오더, 배정 작업, 납기 지연, 최우선 병목 후보를 보여줍니다.
- 실행 모달에서 명시적 우선순위, 납기 우선(EDD), 최단 가공시간 우선(SPT) 중 하나를
  직접 선택하며 서버가 규칙을 자동 추천하지 않습니다.
- 실행 결과 배너에서 적용 규칙, 총 납기 지연시간, Makespan과 계획 설비 가동률을 함께 비교합니다.
- 최신 실행에서 동결 기준시각과 규칙을 선택해 시작·진행 작업을 유지한 새 계획을 만들고,
  결과 배너에서 원본 실행과 동결 기준을 확인할 수 있습니다.
- 스케줄 실행과 재스케줄링은 비동기 실행 ID를 먼저 받은 뒤 완료 또는 실패까지 상태를 조회하고,
  완료된 ScheduleRun 결과를 자동으로 다시 불러옵니다.
- 설비별 간트는 저장된 최신 스케줄의 가공 시작·종료, Changeover 준비작업, 오더 구분과 지연 여부를 표현합니다.
- 설비 부하는 계획기간의 `(가공 분 + Changeover 분) / 가용 분`으로 표시하고, 병목 순위와
  사유는 백엔드 Bottleneck Detection API 결과를 사용합니다.
- 간트와 CAPA 조회는 실행에 저장된 계획 UTC offset을 사용하므로 브라우저 위치와 무관하게 공장 현지시각을 유지합니다.
- 생산오더 화면에서 DRAFT 오더를 확정할 수 있습니다.
- 마스터 화면에서 공장, 라인, 설비, 품목, Routing과 주간 근무시간을 등록할 수 있습니다.
- 사용자 가이드에서 샘플 데이터를 4단계로 등록하고 각 단계의 진행 상태를 확인할 수 있습니다.
- 사용자 가이드에서 샘플 CSV를 내려받고 DB 반영 없이 성공·실패 예상 행과 오류를 미리 확인할 수 있습니다.
- API 오류는 화면 알림으로 표시하고 서버 연결 상태를 왼쪽 하단에서 확인할 수 있습니다.

## 4. 샘플 온보딩

처음 사용하는 사용자는 각 등록 화면을 오가며 값을 직접 입력하지 않고 사용자 가이드의
샘플 온보딩을 따라 첫 스케줄을 만들 수 있습니다.

사용자 가이드는 APS 학습 화면의 진입점입니다. APS의 입력·엔진·출력 관계와 ERP·MRP·MES의
경계를 먼저 설명하고, 기초부터 계획 변경과 운영까지 여섯 학습 과정을 제시합니다. 모든 실습은
`개념 → 예상 → 실행 → 관찰 → 해설` 순서를 사용합니다. 현재 4단계 샘플 온보딩은 과정 A의
첫 실습을 수동 단계로 풀어낸 흐름입니다. 가이드의 실습 카드는 서버 카탈로그를 조회합니다.
첫 생산계획, 유한 CAPA, 공정 선후관계,
납기 지연 카드는 실행 전 질문과 관찰 포인트를 보여 주며, 버튼 한 번으로 격리된 데이터를 생성하고
해당 인스턴스 오더만 계산한 뒤 스케줄 보드로 이동합니다.

시나리오 카드를 누르면 먼저 Priority·EDD·SPT의 총 지연, 지연 오더, Makespan, 가동률과 오더
순서를 3열로 비교합니다. 추천 표시는 설명 가능한 KPI 우선순위에 따른 참고값이며, 사용자가 고른
규칙의 `이 규칙으로 확정 실행` 버튼을 눌러야 실제 ScheduleRun과 오더 상태가 변경됩니다.

규칙 비교 아래의 제약 영향 영역은 같은 오더의 제약 제거 기준과 제약 적용 결과를 2열로 보여 줍니다.
Makespan, 총 지연, 전환시간, 사용 설비 수와 오더 순서를 먼저 비교한 뒤 작업 목록에서 실제 설비와
시각을 확인할 수 있습니다.

`FROZEN_HORIZON` 카드는 기준 계획, 취소·긴급오더와 정비가 반영된 재계획을 한 번에 생성합니다.
가이드는 동결 기준과 정비 구간, 전후 Makespan·지연 KPI를 먼저 보여 주고 각 작업을 고정·이동·제외·
신규로 색상 구분합니다. 작업별 전후 시각과 변경 이유를 함께 표시하므로 경계와 겹친 작업이 왜
끝까지 유지되는지 간트로 이동하기 전에 이해할 수 있습니다.

과정 F의 `MEDIUM_FACTORY`는 12설비·150오더, `PERFORMANCE`는 20설비·600오더를 결정론적으로
생성하고 비동기 계획을 실행합니다. 최신 실행 화면은 전체 KPI 요약과 첫 작업 페이지를 분리해
읽습니다. 간트 도구에서 설비, 오더·공정 검색어, 시작·종료 범위와 페이지를 선택할 수 있고 현재
페이지 최대 100작업만 그립니다. 생산오더 화면도 검색어·상태와 이전/다음 페이지를 서버에 요청합니다.

학습 진도 영역은 과정 A~F별 완료 수와 전체 완료 수를 보여 줍니다. 시나리오 카드는 시작 전, 준비됨,
결과 확인, 완료, 데이터 재확인 상태를 표시하고 현재 브라우저를 다시 열어도 이어집니다. 저장된
인스턴스가 초기화됐으면 완료 표시를 그대로 신뢰하지 않고 데이터 재확인으로 바꿉니다.

결과 코치는 선택한 실습의 관찰 질문, KPI 정의, 실제 결과를 반영한 이유와 다음 실험을 한 영역에
보여 줍니다. 규칙 비교는 추천 규칙, 제약 실습은 Makespan 증감, Frozen Horizon은 고정·이동·제외·
신규 건수, 대량 계획은 전체 오더·작업 수를 정적 해설에 결합합니다. 코치나 진도 저장이 실패해도
생산계획 실행 버튼과 결과 화면은 계속 동작합니다.

```text
1. DEMO-FACTORY · DEMO-LINE · 절단/조립 설비 · 월~금 근무시간
2. DEMO-PRODUCT · DEMO-ROUTING · 절단 → 조립 공정
3. 우선순위가 다른 확정 생산오더 2건
4. Forward Scheduling 실행 · 스케줄 보드 확인
```

- 한 단계가 완료되어야 다음 단계 버튼이 활성화됩니다.
- 등록 중인 항목과 완료 단계는 진행 로그와 진행률로 표시합니다.
- 샘플 코드를 가진 데이터가 이미 있으면 새로 만들지 않고 재사용합니다.
- 단계 도중 요청이 실패해도 완료된 데이터는 유지하며 같은 단계에서 이어서 진행합니다.
- 기존 데이터는 수정하거나 삭제하지 않습니다.
- 직접 입력하려는 사용자는 기존 마스터 데이터와 생산오더 등록 화면을 그대로 사용할 수 있습니다.

샘플 값과 단계 제어는 브라우저 코드에만 있으며, 별도의 샘플 전용 백엔드 API를 추가하지 않습니다.
각 등록은 기존 `/api/v1/**` 계약을 그대로 사용하므로 실제 운영 흐름과 같은 검증을 거칩니다.

## 5. 데이터 흐름

화면은 동일 출처의 `/api/v1/**` API를 호출합니다. 별도 프록시나 CORS 설정은 필요하지 않습니다.
등록 성공 후 해당 계층을 다시 조회해 서버 데이터를 화면 상태의 기준으로 사용합니다.

생산오더는 최초 20건을 읽고 검색·상태 필터와 서버 페이지로 이동합니다. 최신 ScheduleRun은 작업을
포함하지 않는 요약을 먼저 읽고, 작업은 별도 범위 API에서 최대 100건만 가져옵니다. 공장·품목 등
기준정보 목록은 아직 화면별 최대 100건 조회를 사용합니다.

## 6. 제외 범위

- 사용자 인증과 권한
- 기준정보 수정 및 삭제
- 스케줄 확정, 취소와 여러 재스케줄링 이력 비교
- Drag & Drop 수동 재배치
- Maintenance와 대체 설비 시각화
- 서버 푸시 또는 실시간 자동 갱신
- BOM·자재·작업자·금형 제약과 전역 최적화 Solver
- 사용자 계정 기반 학습 진도 동기화

다음 학습 확장 후보는 BOM·자재 가용성, 복수 목적함수 가중치 실험, 교대·공휴일 캘린더,
MES 실적 기반 rolling rescheduling, 사용자가 입력 하나를 바꿔 전후를 저장하는 실험 복제입니다.

## 7. 실행 및 확인

PostgreSQL을 실행하고 로컬 프로필로 애플리케이션을 시작한 다음
`http://localhost:8080`에 접속합니다.

```powershell
docker compose up -d postgres
.\scripts\run-local.ps1
```

처음 실행한다면 `사용자 가이드`에서 샘플 온보딩의 1~4단계 버튼을 순서대로 누릅니다.
직접 검증하려면 마스터 데이터를 구성하고 생산오더를 확정한 뒤 스케줄을 실행합니다.
실행 요청 직후 진행 안내가 표시되고 완료 후 최신 실행 ID, 설비별 간트, 오더 상태와 CAPA 부하가
API 데이터와 일치하는지 확인합니다.
