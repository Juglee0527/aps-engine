# Cache Strategy

## 1. 결정

2026년 8월 8일 문서 현행화 시점에도 Redis 캐시는 도입하지 않습니다.

현재 조회 경로에는 반복 호출량, 응답 지연 또는 데이터베이스 부하가 병목이라는 측정 근거가 없습니다.
외부 저장소와 장애 지점을 늘리기보다 PostgreSQL을 단일 원본으로 유지하는 편이 현재 규모와 운영 단계에
더 안전합니다.

이 결정은 Redis를 사용하지 않겠다는 영구 정책이 아니라, 측정 근거가 생길 때까지의 도입 보류입니다.

## 2. 확인한 구조적 근거

APS Schedule Control Tower는 다음 시점에만 전체 데이터를 다시 조회합니다.

- 최초 화면 진입
- 사용자의 `데이터 새로고침`
- 기준정보, 생산오더, 근무시간 또는 스케줄 쓰기 작업 완료

주기적 polling이나 백그라운드 자동 새로고침은 없습니다. 현재 UI 사용 흐름에서는 같은 캐시 키를 짧은
시간에 반복 조회할 가능성이 낮습니다.

| 조회 경로 | 현재 비용 | 변경 원인 | 판단 |
| --- | --- | --- | --- |
| `GET /api/v1/schedules/latest` | ScheduleRun과 작업 결과 EntityGraph 조회 | 새 스케줄 실행 | 잠재 후보지만 호출 빈도·지연 근거 없음 |
| `GET /api/v1/schedules/{id}` | 특정 실행 결과 EntityGraph 조회 | 저장 후 불변 | 현재 UI 반복 호출 없음 |
| `GET /api/v1/schedules/{id}/lead-times` | 저장 작업 조회와 메모리 합산 | 저장 후 불변 | 현재 UI에서 호출하지 않음 |
| `GET /api/v1/schedules/{id}/bottlenecks` | 실행, 캘린더, 정비 일괄 조회와 CAPA 계산 | 스케줄·캘린더·정비 변경 | 무효화 범위가 넓어 섣부른 캐시 위험 |
| 기준정보 목록 | 페이지 또는 소속별 조회 | 각 기준정보 쓰기 | 키 조합과 무효화가 많고 데이터 규모가 작음 |

특히 병목 진단은 저장된 스케줄만 사용하는 값이 아닙니다. 동일 ScheduleRun ID라도 WorkingCalendar나
Maintenance가 바뀌면 가용 CAPA가 달라지므로 스케줄 키만 캐시하면 오래된 진단을 반환할 수 있습니다.

## 3. 이번 단계에서 추가하지 않은 것

- Redis와 Spring Cache 의존성
- 캐시 서버 환경변수와 Docker 구성
- 애플리케이션 내부 임시 캐시
- 캐시 장애 우회 코드

적용할 조회가 선정되지 않은 상태에서 장애 우회 코드만 추가하면 검증 대상과 운영 복잡도만 늘어납니다.
따라서 “캐시 장애 시 원본 조회” 테스트도 실제 캐시 도입 단위에서 함께 작성합니다.

## 4. 재검토 기준

운영 또는 성능 기준선에서 아래 중 하나가 관측되면 캐시 도입을 다시 검토합니다.

- 동일 조회 키의 반복 요청이 전체 요청의 70% 이상
- 읽기 API의 p95 응답시간이 150ms를 지속적으로 초과
- 해당 조회가 데이터베이스 시간 또는 쿼리 수의 주요 병목으로 확인
- 다중 애플리케이션 인스턴스가 동일 조회 결과를 공유해야 함

재검토 시 먼저 요청 수, p50/p95, SQL 실행 수와 예상 적중률을 기록합니다. 캐시 적용은 근거가 확인된
읽기 전용 경로 하나로 제한합니다.

## 5. 향후 도입 시 필수 계약

실제 도입 단위에는 다음 내용을 함께 확정해야 합니다.

- 키: 도메인 식별자와 결과에 영향을 주는 버전 또는 변경 시각 포함
- TTL: 허용 가능한 데이터 신선도에 근거해 설정
- 무효화: 관련 쓰기 트랜잭션 성공 후 수행
- 장애 정책: Redis 연결 실패 시 PostgreSQL 원본 조회로 fail-open
- 테스트: cache hit, 쓰기 후 무효화, Redis 장애 시 원본 조회

Redis를 적용하기 위해 도메인 정확성을 낮추거나 쓰기 트랜잭션을 캐시에 의존시키지 않습니다.
